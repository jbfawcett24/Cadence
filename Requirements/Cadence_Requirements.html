Cadence

Requirements Specification

Team member: James Fawcett

Course: CSE 499 Senior Project

Document date: October 30, 2026

Project description: Cadence is an offline-first desktop sheet-music reader for Windows and Linux hybrid laptops and tablets. It lets musicians import, organize, read, annotate, navigate, and practice scores without paper binders, an iPad, or an internet connection.

Section 1: Introduction

Why this project?

Musicians often carry paper binders or depend on a specific tablet platform to access music during rehearsals and performances. Paper scores are difficult to organize and annotate consistently, while many digital workflows assume an iPad, a cloud account, or a network connection. Cadence addresses this problem by providing a focused sheet-music reader that runs on Windows and Linux devices, including touchscreen hybrid laptops and tablets.

Purpose

The purpose of Cadence is to provide musicians and music educators with a dependable local application for managing and reading digital sheet music. The application will import PDF and MusicXML scores, display them in a performance-friendly reader, support stylus annotations, provide touch and pedal navigation, organize scores into a searchable library and setlists, and play a MusicXML pitch/tempo reference. Core workflows will remain available when network access is disabled.

Scope

Cadence will include local score import, PDF and MusicXML reading, page navigation, portrait and landscape layouts, pen/highlighter/eraser annotation, palm-rejection behavior on tested hardware, local persistence, library metadata and search, setlists, MusicXML playback, and offline validation. Stretch work includes linking external MP3/WAV tracks to PDF scores, undo/redo, exporting annotated PDFs, and a visual metronome.

Cadence will not require a cloud backend, user account, online synchronization, proprietary service, advanced audio mixing, or a guarantee of compatibility with every stylus, Bluetooth pedal, Windows device, or Linux input stack. Hardware support will be reported only for devices actually tested.

Technologies Used

  • Tauri 2 and Rust for the cross-platform desktop shell, local filesystem commands, managed score storage, and safe persistence.
  • React, TypeScript, Vite, and Emotion for the touchscreen-first user interface.
  • PDF.js for multi-page PDF rendering and canvas-based display.
  • A MusicXML notation renderer to be selected and documented before implementation (OpenSheetMusicDisplay or Verovio).
  • Local JSON files behind repository interfaces for the initial storage engine; the UI will not depend directly on the storage format.
  • Web Pointer Events and vector stroke data for annotations; Tauri dialog support for local file selection.

Section 2a: Must Have Requirements

Each requirement below is written as a functional “shall” statement. The success measure describes an observable demonstration rather than a code inspection.

IDRequirementSuccess measure and demonstration
FR-01The system shall import and open multi-page PDF scores.Import a sample multi-page PDF while offline, open it from the library, and view every page in the reader.
FR-02The system shall import and render MusicXML scores as readable musical notation.Import a standard MusicXML fixture, open it, and show readable notation in the score reader.
FR-03The system shall provide usable zoom, pan, page caching, and high-DPI-aware score rendering.Zoom and pan a score, change pages, and verify that the view remains legible without an unacceptable reload delay or visual degradation.
FR-04The system shall adapt the score layout to portrait and landscape orientation.Resize or rotate the window: portrait displays one page and landscape displays a two-page spread while preserving the current reading position.
FR-05The system shall navigate forward and backward through scores using touch controls and configurable keyboard/HID pedal keys.Advance and return through a sample score using touch edge zones or taps, then repeat with mapped PageUp/PageDown or equivalent HID pedal events.
FR-06The system shall provide pen, highlighter, and eraser annotation tools.Draw a pen mark, draw a distinguishable translucent highlighter mark, erase each mark, and observe the result in the reader.
FR-07The system shall distinguish pen input from touch input for palm-rejection behavior.On a tested stylus touchscreen, draw with the pen while resting a palm or finger on the display; touch contact shall not create unwanted ink. Any device limitation shall be documented.
FR-08The system shall smooth pen input into continuous vector strokes and preserve score alignment during zoom and pan.Make a fast stroke, zoom and pan the page, and verify that the stroke is visually continuous and remains aligned with the score.
FR-09The system shall persist annotations by score page for both PDF and MusicXML documents without modifying the original score.Annotate a PDF and a MusicXML score, close and relaunch the application, and verify that marks return on the same pages and the original files are unchanged.
FR-11The system shall organize imported scores in a local library with metadata and offline search by title, composer, instrument, or tag.Import several scores with metadata, place them in folders, search each supported field while offline, and verify that matching scores are returned.
FR-12The system shall allow a user to create, reorder, save, open, and navigate an ordered setlist.Create a three-piece setlist, reorder the pieces, close and reopen it, and perform through the pieces without returning to the library between scores.
FR-13The system shall synthesize and play MusicXML notes with play/pause and tempo control.Open a standard MusicXML fixture, start playback, pause it, change tempo, and hear the score play at the selected tempo.
FR-15The system shall provide a clear, touchscreen-first interface suitable for rehearsal and performance.Using touch only, import/open a score, reach primary reader controls, change tools, and navigate without controls obscuring the readable score. Controls shall have visible active states and usable touch targets.

Section 3: Design Overview of the Product

Workflow

The primary workflow begins with a local score file and ends with a readable, annotated, reusable performance resource:

Choose local PDF or MusicXML
        |
        v
Validate format and copy score into managed local storage
        |
        v
Create metadata record -> library/folders -> optional setlist
        |
        v
Open score -> renderer displays pages/notation
        |
        +--> touch, keyboard, or HID pedal changes page/viewport
        +--> pen/highlighter creates page-relative vector annotation
        +--> eraser removes selected stroke
        +--> MusicXML playback produces local pitch/tempo reference
        |
        v
Persist library, setlist, settings, and annotations locally
        |
        v
Close/relaunch -> restore the same score and user data

Resources

Development resources include a Windows or Linux x86_64 computer, an available touchscreen hybrid laptop or tablet, a supported active stylus when available, a keyboard or Bluetooth HID pedal for navigation testing, representative PDF/MusicXML fixtures, and local MP3/WAV fixtures for the stretch audio feature. The project uses the repository’s React/TypeScript/Tauri/Rust toolchain, npm, Cargo, and the libraries listed in Section 1.

Data at Rest

Imported PDF and MusicXML files are copied into an application-managed library directory; the original files are never moved or deleted. Library metadata, folders, setlists, page-organized annotations, audio links, and settings are stored locally as separate JSON files behind persistence interfaces. Scores and setlists use stable IDs. Linked MP3/WAV files initially remain at their original local paths. The application does not require a profile, login, cloud account, or network database.

Data on the Wire

Cadence has no required remote network service and does not transmit score, annotation, or audio data. Data moves locally between the React/TypeScript frontend, application services, persistence interfaces, and explicit Tauri/Rust commands. File selection and managed local-file resolution occur through Tauri APIs. Core workflows must continue with network access disabled.

Data State

Library source file
  -> validated managed score copy
  -> Score metadata record (id, title, composer, tags, format, folder)
  -> renderer state (active page, viewport, orientation)
  -> page annotation document (ordered vector strokes)
  -> persisted JSON records
  -> restored application state after relaunch

Setlist state: ordered stable score IDs -> performance navigation -> next score
Audio state: optional local link -> availability check -> playback state

HMI/HCI/GUI

The interface is designed around a library view and a score-reader view. The library presents imported scores, folders, metadata, search, and setlists. The reader prioritizes the score surface and keeps primary actions—back, page navigation, orientation, annotation tool selection, and playback—visible but unobtrusive. Touch controls use large targets; keyboard/HID alternatives are available for page turning. The active tool is visibly indicated, errors are shown in the interface, and score content remains the dominant visual element.

+----------------------------------------------------------+
| Cadence | Back | Library | Setlist | Pen | Highlighter  |
|----------------------------------------------------------|
|                                                          |
|                 SCORE / NOTATION SURFACE                |
|             annotation layer above score                |
|                                                          |
|  < previous       page / spread       next >             |
|----------------------------------------------------------|
| Play/Pause | Tempo | Zoom | Eraser | Settings           |
+----------------------------------------------------------+

Architecture

The dependency direction is UI components → application services → persistence interfaces → Tauri/Rust filesystem implementation. Rendering, annotations, library/setlists, audio, and persistence are separate responsibilities. This structure permits the initial JSON storage to be replaced by SQLite later without requiring UI components to access storage APIs directly.

Section 4: Verification

Demo

The final demonstration will be performed entirely offline using a multi-page PDF, a MusicXML score, and representative annotation fixtures. The demonstration will import both scores, add them to a setlist, open and navigate them in portrait and landscape, use touch and a tested keyboard/HID pedal input, draw and erase annotations with a tested stylus, close and relaunch to show persistence, and play the MusicXML score with synthesized notes, pause, and tempo control. If stretch items are complete, the demonstration will also show MP3/WAV linking, undo/redo, annotated-PDF export, and/or the visual metronome.
